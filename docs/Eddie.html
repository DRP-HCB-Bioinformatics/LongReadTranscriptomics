Eddie

Eddie is a high performance cluster (HPC) within the University of Edinburgh. It is free to use, but can be complex to work with.

Being a HPC means that there are multiple computers tied together. Every machine within the HPC is refer to as a node, however there is one computer which runs all of the other computers. This machine is called a head node or a login node. From here everything is set off. The important thing to know is that our commands will generally not be run on this node, this just the manager.

To log in, use the following command. Replace the with your UUN and make sure you are within the university network.

$ ssh <UUN>@eddie.ecdf.ed.ac.uk

Data Storage

Note: Eddie is not for data storage! It is for processing of data, it is important to store your data in a main storage location

Within the system, there are three main data storage places.

  • Every user will have a home folder of 10GB: /home/<UUN>
  • Every user will have access to scratch which can contain 2 TB of data: /exports/eddie/scratch/<UUN>.
    Files older than a month will be deleted from scratch automatically.
  • Groups have and can access their DataStore on Eddie, by default this is 200GB: /exports/<COLLEGE>/eddie/<SCHOOL>/groups/<GROUP NAME>.
    More information on DataStore can be found here

Running processes

To submit jobs, this cluster uses Grid Engine. With that we can ‘submit’ jobs into a list. The head (or login) node will look at which computers are busy and which computer can take your job and run it. Before looking into how to submit jobs, we will look into what we need to submit jobs.

Job Scripts

To submit jobs, specific scripts are needed. These contain information on how many threads or cores the job should be run on as well as the commands that need to be run. Below an example of a script.

#!/bin/sh
#$ -N hello              
#$ -cwd                  
#$ -pe sharedmem 2
#$ -l h_rss=32G
#$ -l h_rt=00:05:00 

# Initialise the environment modules
. /etc/profile.d/modules.sh

# Load Python
module load python/3.4.3

# Run the program
./hello.py

Important settings are at the top, indicated with #$. Any lines below these lines that start with a # below are comments, other lines are the commands that need to be run.

  • -N is the name that will be used for the job
  • -cwd means it will use the current working directory
  • -pe sharedmem 2 indicates how many threads or cores should be used, in this case 2.
  • -l h_rss=32G is used to set how much memory can be used per core, in this case it would mean 64GB in total over the 2 cores set. This is an option setting, but can be very useful for specific bioinformatic applications.
  • l h_rt=00:05:00 indicates the runtime needed for this job. This indicates 5 minutes. The setup for the time needed is HH:MM:SS

To check what the maximum amount of cores (or slots) and memory is on machines within the cluster, please check here.

Job Submission

To submit jobs and get them to run, the qsub command can be used.

$ qsub script.sh

If the data is being read from or written to a group on the datastore, specific nodes need to be used. To be able to submit to these nodes specifically, use the following command.

$ qsub -q staging script.sh

Once submitted, the cluster will give you a job ID.

Job Status

An important thing to check is what the status is for your jobs. This can easily be done using the qstat command.

$ qstat

If no jobs are currently running or waiting for you, no results will be shown. If there are jobs, information about the state of the job can be seen. A number of different options are available as states.

  • qw means the job is queued and waiting
  • r is a running job
  • s means the job has been suspended
  • Eqw means something has gone wrong in the setup or execution.

Job Cancel

When a job is runnig but something has gone wrong or we realise that something needs to be changed, there is the option to cancel jobs. To cancel a job, we need to have the ID. This can be taken from the submission or the status overview. To cancel the job, the command qdel is used.

$ qdel JOBID

The terminal will tell us that the job has been deleted, freeing up the server for a new job.

Sessions

In some cases, we want to test commands without making it into actual jobs. In those cases we can use interactive sessions. By default, these run for only 48h, so we will look into how to get longer sessions just in case they are needed. If connection is lost to the session, unsaved data or running jobs will be lost, using screen in those cases can be useful.

Screen

screen is a command in Linux which will allow you to run job, disconnect from the server, and come back to reconnect to the session. To be able to reconnect easily, naming a screen session will be useful.

$ screen -R NAME

Nothing much will happen. To double check if the screen has been properly activated, we can disconnect and reconnect to the screen. To disconnect, press Control+A followed by Control+D. This should show a message that the screen has been disconnected. To reconnect to the screen, the following command can be used.

$ screen -r NAME

Once a screen has started, it will stay active until we exit the screen or the machine is restarted. It can be extremely useful when running long commands, however scrolling through the results printed to screen is not allowed within a screen. Make sure to store logs if needed into files to be able to view them completely.

Starting Interactive Session

Once inside a screen, to start an interactive session, use the following command.

$ qlogin

By default, the session is set to only last 48h, uses 1 core and has a maximum of 16GB of memory. To edit these settings, the following can be added to the command.

  • -pe sharedmem 2 can be used to set how many cores need to be available, in this case 2.
  • -l h_rss=32G is used to set how much memory can be used per core, in this case it would mean 64GB in total over the 2 cores set.
  • -l h_rt=HH:MM:SS can be added to adjust the time

And then finally if we need access to the datastore, the following needs to be added.

  • -q staging to be able to get access to the datastore.

All of these can be combined together into a single session request. The following command will request a session with 2 cores, 64GB memory in total, 2 hours of access time, and have access to datastore.

$ qlogin -pe sharedmem 2 -l h_rss=32G -l h_rt=02:00:00 -q staging

It could be that no machines are currently available, try again later in that case. The more requested resources, the more likely it is that no machines are available. If this gets in the way of being able to process data, try writing small scripts to test commands.

Conda environments

Creating conda environments could be essential for working within the system. These can be created within the home folder, however this can cause the home folder to fill up fast. For environments needed for only testing, saving them on the scratch system will be helpful.

To be able to create or use a conda environment, the anaconda module needs to be loaded.

$ module load anaconda

Once anaconda is loaded, conda environments can be created. If the environment needs to be create in a specific location like the scratch drive, the -p option can be used. An example is shown below to create an environment within the scratch directory called bowtie2.

$ conda create /exports/eddie/scratch/<UUN>/bowtie2

Once created, conda can be used in the default way to install tools easily.

$ conda activate /exports/eddie/scratch/<UUN>/bowtie2

$ conda install bowtie2

To be able to use these tools within the scripts, we need to make sure that the environments are activated within them before using them. To be able to run bowtie2, the following script will activate the environment and allows us to run the tool.

#!/bin/sh
#$ -N hello              
#$ -cwd                  
#$ -pe sharedmem 2
#$ -l h_rss=32G
#$ -l h_rt=00:05:00 

# Initialise the environment modules
. /etc/profile.d/modules.sh

# Load Conda
module load anaconda

# Activate the environment
conda activate /exports/eddie/scratch/<UUN>/bowtie2

# Run the program
bowtie2 --help

# Deactivate the environment at the end of the code
conda deactivate

Deactivation is not mandatory, but will make sure nothing strange has happened to the environment and keep it clean.
